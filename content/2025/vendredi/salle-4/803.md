# Crossplane: Déployer vos composants Cloud depuis votre K8S sans drift

**Vivien Ramahandry — Vendredi 7 novembre 2025 — Salle 4 (D1+D2)**

## État de la transcription

**Carnet partiel : le besoin, le problème de drift et le début de l'explication des contrôleurs sont disponibles.** La transcription coupe avant la mise en œuvre de Crossplane et ne contient ni démonstration complète ni conclusion.

## Une application Kubernetes dépend aussi de ressources externes

Vivien Ramahandry présente son expérience de lead SRE chez Jump. Son rôle consiste notamment à aider les équipes à déployer leurs applications dans Kubernetes et dans le cloud. Le cas de départ est une API backend qui ne fonctionne pas seule : elle a besoin d'un bucket pour des documents, d'une messagerie ou d'une base de données.

Ces ressources externes sont couramment décrites avec de l'infrastructure as code. Un fichier représente l'état attendu et un outil, comme Terraform ou OpenTofu, applique cette configuration à l'infrastructure réelle. L'extrait part de ce fonctionnement pour expliquer où les écarts peuvent apparaître.

## Le drift comme divergence entre description et réalité

Une personne modifie directement un paramètre dans le cloud, par exemple une permission sur un bucket, sans reporter le changement dans le code. Plus tard, une autre modification est appliquée à partir de la configuration conservée dans le dépôt. Le résultat peut supprimer ou modifier une adaptation dont l'application dépendait.

L'incident ne vient alors pas simplement du dernier changement demandé. Il révèle une divergence préalable entre la description de référence et l'état réel. Vivien nomme ce phénomène le drift et annonce Crossplane comme l'une des approches permettant de le traiter.

## Étendre Kubernetes à d'autres ressources

Crossplane est présenté comme un projet open source qui étend les capacités de Kubernetes au pilotage de ressources situées en dehors du cluster, notamment des composants cloud. Dans l'approche décrite, il nécessite donc un cluster Kubernetes et s'appuie sur des objets de configuration YAML.

Les repères de maturité et de version cités pendant l'intervention appartiennent au contexte de novembre 2025. Ils sont rapportés comme le cadrage du talk et non comme un état actuel du projet.

## Le principe de réconciliation

Vivien commence une digression sur le fonctionnement de Kubernetes. Des contrôleurs comparent un état souhaité à la situation réelle. L'exemple porte sur deux réplicas : si un serveur tombe et qu'un conteneur disparaît, un contrôleur cherche à recréer ce qui manque pour retrouver le nombre attendu.

La transcription s'arrête pendant cette explication. Elle ne montre pas comment le principe est appliqué concrètement à une ressource cloud avec Crossplane. Les providers, les permissions, les objets utilisés, la démonstration de correction du drift et les limites éventuelles ne peuvent donc pas être détaillés à partir de ce fichier.
