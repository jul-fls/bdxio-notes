# Remplacer votre IDE par un CDE pour un embarquement immédiat !

**Ivan Béthus · Nicolas Guilhem — Vendredi 7 novembre 2025 — Amphi A**

## Partir d'un onboarding qui déraille

Ivan Béthus et Nicolas Guilhem commencent par une scène de dépannage. Un développeur rejoint un projet et suit une documentation d'installation qui n'a pas été entretenue. Son système d'exploitation, la version de Java et les outils nécessaires compliquent immédiatement les choses. Le faux départ sur une conférence consacrée aux API REST fait partie de cette mise en scène : le véritable sujet est l'environnement de développement.

L'objectif est de rendre l'environnement explicite et reproductible. Le dépôt doit pouvoir expliquer ce qu'il faut installer et comment travailler, sans dépendre exclusivement d'une liste d'instructions exécutées à la main. Les démonstrations avancent progressivement, d'un conteneur local jusqu'à une machine distante accessible depuis l'éditeur.

## Décrire l'environnement avec les Dev Containers

Une configuration Dev Container permet de définir un environnement et d'y connecter son outil de développement. Elle peut préciser les outils, les extensions et des réglages utiles. Une configuration très courte suffit pour une première démonstration ; le cas plus réaliste ajoute les besoins du projet et un environnement frontend à côté du backend Quarkus.

Le fichier de configuration rejoint le code du projet. Si les versions ou les outils changent, l'environnement peut évoluer dans la même modification. Les personnes qui rejoignent le projet profitent ainsi d'une configuration partagée au lieu de recommencer chacune la procédure d'installation.

Les démonstrations montrent aussi les dépendances qui tournent dans d'autres conteneurs. L'accès au démon Docker de la machine hôte permet de lancer ces services depuis l'environnement de développement. Les intervenants distinguent ce fonctionnement du cas où un Docker supplémentaire tournerait entièrement dans le conteneur.

## Passer de la machine locale au CDE

Le Cloud Development Environment déplace l'exécution sur une infrastructure distante. L'éditeur devient le point d'accès à un environnement qui ne dépend plus uniquement des ressources du poste. La présentation parcourt plusieurs solutions : Eclipse Che dans l'écosystème Kubernetes, DevPod avec ses providers, les offres managées et Coder pour une approche auto-hébergée.

Le fichier Dev Container peut rester un point commun entre ces approches. Il faut néanmoins distinguer la description des outils de la création effective de l'infrastructure. Dans Coder, les templates s'appuient sur Terraform ; le choix de l'hébergement, des ressources et du réseau demande donc des compétences supplémentaires.

## Les contraintes visibles pendant les démonstrations

Déplacer l'environnement ne fait pas disparaître les besoins d'exploitation. Une plateforme Kubernetes ou Coder nécessite des machines, une configuration et des personnes pour s'en occuper. Le coût et la complexité dépendent de la taille de l'équipe et de la solution retenue. L'option managée simplifie une partie de ce travail mais change le compromis.

Les questions portent aussi sur la connexion réseau, les ports nécessaires et la personnalisation : comment retrouver sa configuration Git, ses alias ou son shell ? Ces sujets comptent pour l'adoption quotidienne. Le bilan est pragmatique : versionner l'environnement avec le code aide l'embarquement et les mises à jour, mais une équipe doit choisir jusqu'où elle veut aller dans la centralisation et dans l'exploitation de sa plateforme.
