# Les coulisses de JavaScript : ce qu’on utilise sans comprendre 🎭

**Etienne Idoux · Mickael Alves — Vendredi 7 novembre 2025 — Amphi A**

## Comprendre ce qui exécute réellement le code

Étienne Idoux et Mickael Alves construisent leur présentation comme les coulisses d'un spectacle. Les effets visibles du programme dépendent de plusieurs mécanismes que l'on utilise tous les jours sans toujours les distinguer. Le parcours commence par l'histoire de JavaScript, créé pour le navigateur Netscape en 1995, puis suit son évolution jusqu'au langage utilisé aujourd'hui dans les navigateurs et côté serveur.

Un point important est la distinction entre le moteur JavaScript et son environnement d'exécution. Le moteur traite le code ; le navigateur ou Node.js fournit aussi des services autour de lui. Une fonction familière comme setTimeout appartient à cet environnement. Comprendre cette séparation permet d'éviter d'attribuer toutes les opérations au langage lui-même.

## La pile d'appels et les opérations asynchrones

La call stack garde la trace des fonctions en cours d'exécution. Appeler une fonction ajoute un cadre ; terminer cette fonction le retire. Une récursion sans arrêt remplit progressivement la pile jusqu'au débordement. Le caractère single thread s'observe dans cette exécution d'une chose à la fois sur la pile.

Un minuteur ne bloque pas le moteur pendant toute son attente. L'environnement prend en charge l'attente, puis rend le callback disponible. Il reste encore à pouvoir l'exécuter. C'est la différence entre le moment où une tâche devient prête et le moment où le programme lui donne effectivement la main.

L'event loop relie la pile aux files de travail. Tant que du code synchrone occupe la pile, les callbacks en attente ne viennent pas l'interrompre. Une durée passée à setTimeout ne garantit donc pas que le callback démarrera exactement à cette échéance. Les démonstrations invitent à prédire les affichages console avant de suivre leur passage dans les différentes structures.

## Promesses, tâches et microtâches

Les promesses ajoutent une autre file à considérer. Leurs réactions ne suivent pas simplement le même chemin que les callbacks des minuteurs. La distinction entre tâches et microtâches explique des ordres d'affichage qui semblent surprenants si l'on ne regarde que l'ordre des lignes.

La présentation ouvre aussi la promesse comme un objet interne : un état, un résultat et des réactions enregistrées pour les issues possibles. Ajouter un then ou un catch enregistre le travail à effectuer lorsque l'issue correspondante sera connue. Résoudre une promesse et exécuter la réaction sont deux moments à distinguer dans le raisonnement.

## Contextes d'exécution, portée et hoisting

La dernière partie passe de l'asynchronisme à l'organisation des variables. Un contexte d'exécution conserve les informations nécessaires au code et s'inscrit dans une chaîne de portées. Pour retrouver une variable, on cherche dans le contexte courant, puis dans les contextes accessibles autour de lui.

Les phases de création et d'exécution éclairent le hoisting. var, let et const ne présentent pas le même comportement avant leur déclaration effective. La zone morte temporelle empêche notamment certains accès prématurés avec let et const. L'enjeu pratique est de remplacer les recettes apprises par cœur par une simulation précise : quels contextes existent, quelles variables sont initialisées, quelle pile est occupée et quelle file attend son tour ?
