# Microservices Kotlin Benchmark : coroutine, virtual thread, grpc, http, ... le match !

**Xavier Hanin · Vendredi 8 novembre 2024 · Salle 1 (F1+F2)**

## Le point de départ

Xavier Hanin présente des choix de stack serveur à partir de son expérience chez 4SH. L’équipe travaille sur des applications JVM avec Java et Kotlin, des bases MongoDB ou relationnelles, des API HTTP et des échanges gRPC. L’arrivée des virtual threads avec Java 21 lui donne une raison de comparer plusieurs façons de gérer la concurrence. Certaines applications utilisent déjà les coroutines Kotlin, d’autres des threads de plateforme.

La transcription reçue passe des préparatifs au début de l’exposé autour de 31 min 30 s. Elle s’arrête à 48 min 33 s, au moment où Xavier décrit le lancement du premier test. Les résultats et la conclusion restent à compléter.

## Ce qu’il veut comparer

Le benchmark confronte plusieurs solutions sur un même travail applicatif. Pour HTTP, Xavier évoque Spring Boot avec des threads de plateforme ou des virtual threads, puis Ktor avec les coroutines. Côté gRPC, il présente Armeria. Il souhaite observer le débit et les différences de comportement sur un service qui attend des réponses d’autres systèmes.

Il annonce qu’il ne cherche pas à régler finement chaque framework. Ce parti pris limite le temps consacré aux paramètres des pools et évite que le résultat reflète surtout sa capacité à optimiser une solution particulière. C’est un point à garder en tête pour interpréter la comparaison lorsque les mesures seront disponibles.

## Le scénario exécuté par chaque serveur

L’opération recherche des personnes par nom dans MongoDB. Pour chaque personne retournée, elle construit une zone géographique, effectue un comptage en base et interroge un autre service pour récupérer des points d’intérêt. Le résultat agrège ces informations.

Xavier souligne que le scénario contient volontairement des appels de type N+1. Il aurait été possible de demander directement un comptage au service de points d’intérêt. Il choisit de récupérer des données pour provoquer des échanges réseau. L’objectif est de solliciter les entrées-sorties et la concurrence avec un scénario assez simple pour être reproduit d’une stack à l’autre.

La base contient 100 000 personnes. Les noms ont été organisés pour retrouver un ensemble de personnes, mais le nombre de résultats retournés est limité à deux dans l’exemple présenté. Ce paramètre contrôle aussi le nombre d’appels supplémentaires. Le faire varier permettrait d’observer un autre profil de charge.

## Isoler autant que possible le serveur testé

Le serveur de points d’intérêt simule le travail attendu pour éviter d’être lui-même le facteur limitant. La base dispose de ressources prévues pour supporter les tests. La génération de charge utilise k6, lancé dans Kubernetes sur GKE, comme les autres composants.

Le générateur reçoit davantage de CPU que le serveur testé. Xavier explique notamment que les tests gRPC peuvent coûter davantage au client de charge. Il prête aussi attention au placement des composants sur les nœuds pour éviter qu’un voisin consomme les ressources du serveur mesuré.

## Lire la configuration réellement exécutée

À la fin de l’extrait, Xavier distingue le nombre d’utilisateurs virtuels indiqué sur une diapositive de celui visible dans l’outil. Le paramétrage effectif prévaut pour lire le test. C’est précisément à cet endroit que la transcription s’arrête : elle ne permet pas encore d’attribuer un gain à une stack ou à un modèle de concurrence.

## Ce que j’en garde

Avant de comparer des chiffres, vérifier le scénario, les limites de ressources, le nombre d’appels en cascade et les dépendances. La préparation du benchmark montre comment un détail de configuration peut modifier ce que l’on mesure.
